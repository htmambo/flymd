# 插件隔离设计（后续项）

## 现状与问题

插件代码通过 Blob URL 以 ESM 形式加载到主窗口，与宿主同 realm：

- 可直接访问 `window.__TAURI_INTERNALS__`、`document`、`fetch`、`localStorage`；
- 主窗口 capability 授予 `fs:allow-*` 且 scope 为 `"**"`，`assetProtocol.scope` 也是 `"**"`；
- `pluginInvoke` 的 JS 名单只能防误用，不能阻止恶意插件（见 `plugin-invoke-boundary.md`）。

本轮已完成的缓解：名单与命令表契约、Rust 侧参数校验、安装路径净化、安装前风险确认。
这些降低了“误用/供应链粗糙攻击”的概率，但一旦插件代码是恶意的，仍以应用权限运行。

## 威胁模型

- 恶意第三方插件（市场/GitHub 安装）读取 `~/.ssh`、浏览器数据、任意文档；
- 插件删除/篡改用户文件；
- 插件把宿主当作 SSRF/下载/提权原语；
- 插件注入 UI（伪登录框）或监听键击。

## 方案对比

### A. 独立 Webview + 消息桥（推荐的第一步）

- 插件运行在独立 `WebviewWindow`（独立 label），只注入受限的 `postMessage` 桥；
- 主窗口不再向插件窗口授予自定义命令权限；桥只暴露白名单方法（读当前文档、写当前文档、通知等）；
- 宿主侧对每个桥方法做参数校验与用户确认（写文件/网络）。
- 优点：改动集中在窗口创建与桥；缺点：插件 UI 集成（面板/侧栏）需要重做；Tauri 的 capability 按 label 配置，天然隔离文件系统。
- 迁移：先支持“无 UI 的后台插件”（如发布、同步），面板类插件留在主窗口并标记为 trusted。

### B. Sidecar 进程 + JSON-RPC

- 插件在独立进程运行，宿主通过 stdio/本地 socket 通信；
- 优点：最强隔离（崩溃/内存/权限都可控）；缺点：需要为每个平台打包运行时，插件 API 全部要重新设计，迁移成本最高。

### C. 保持同 realm + 权限声明（过渡）

- 在 manifest 增加 `permissions` 声明（fs.read / fs.write / net / ui），安装时展示并由宿主强制执行；
- 优点：改动小、可渐进；缺点：JS 层强制仍可被绕过，只能作为“知情同意 + 误用防护”，不是安全边界。
- 建议作为 A 落地前的过渡，并与安装确认 UI 合并。

## 推荐路线

1. **短期（已做）**：命令契约、Rust 参数校验、安装路径净化、安装风险确认。
2. **中期**：方案 C 的 `permissions` 声明 + 安装确认展示；把高危命令（任意读写、git、office、更新）从公开 API 移除。
3. **长期**：方案 A，先在 1~2 个官方插件上试点（如 typecho-manager、git-history），再推广。

## 验收标准（方案 A 试点）

- 插件窗口无法直接调用 `plugin:fs|*`、`plugin:http|*` 或自定义内部命令；
- 桥方法有单元测试覆盖越界路径/超大参数/未授权调用；
- 官方插件在独立窗口下功能回归清单通过；
- 主窗口 capability 的 `fs` scope 从 `"**"` 收敛到用户主动打开的库根。

## 非目标

- 本轮不实现隔离；仅确定方向与验收标准，避免后续重复讨论。
